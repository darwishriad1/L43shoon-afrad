# منظومة إدارة الفرد والجاهزية العسكرية

هذه نسخة محسّنة من تطبيق **L43shoon-afrad** لإدارة الأفراد والوحدات والحضور والطلبات والتقارير. تم الحفاظ على الواجهة الأصلية مع إصلاح طبقة المصادقة والصلاحيات وكلمات المرور وإضافة فحوصات أمنية وتقسيم أفضل لحزمة الإنتاج.

## المتطلبات

يحتاج التطبيق إلى Node.js 20 أو أحدث، وقاعدة PostgreSQL متوافقة مع إعدادات المشروع. انسخ `.env.example` إلى `.env` ثم عيّن `SQL_HOST`, `SQL_DB_NAME`, `SQL_USER`, `SQL_PASSWORD`، وأنشئ قيمة عشوائية طويلة في `LOCAL_SESSION_SECRET` لا تقل عن 32 حرفًا.

لا تضع ملف `.env` داخل المستودع ولا تستخدم القيمة التجريبية الموجودة في `.env.example`. قيمة `OTP_DEV_CODE` اختيارية للتطوير فقط؛ لا تعتبر بديلًا عن TOTP أو مزود تحقق ثنائي حقيقي في الإنتاج.

## التشغيل

ثبّت الاعتمادات باستخدام `npm install`، ثم شغّل فحص الأنواع واختبارات الأمان بواسطة `npm run lint` و`npm run test:security`. للتطوير استخدم `npm run dev`. لبناء نسخة الإنتاج استخدم `npm run build` ثم شغّلها باستخدام `npm start` بعد ضبط `NODE_ENV=production`.

## ملاحظات أمنية مهمة

جميع مسارات API محمية افتراضيًا بالمصادقة، باستثناء تسجيل الدخول ونقطة OTP العامة. الجلسات المحلية موقعة بمفتاح HMAC وتحتاج إلى `LOCAL_SESSION_SECRET`. كلمات المرور الجديدة تخزن باستخدام scrypt، وكلمات المرور القديمة النصية لا تُقبل إلا لترقية السجل عند أول دخول ناجح. أُزيلت كلمات المرور الافتراضية المبنية على الرقم العسكري أو `123456`.

الحسابات الجديدة القادمة من تسجيل Firebase تُنشأ بحالة `pending` ولا تحصل على صلاحيات مدير تلقائيًا. يجب على مدير النظام اعتمادها ومنح الدور المناسب. عمليات إدارة المستخدمين وإعادة تهيئة قاعدة البيانات والنسخ والاستعادة وتكوين حسابات الأفراد محمية بدور إداري.

## قاعدة البيانات

تمت إضافة قيود uniqueness للحسابات والأرقام العسكرية والحضور المركب داخل مخطط Drizzle. قبل تطبيق المخطط على قاعدة بيانات قديمة، افحص السجلات المكررة أولًا وأنشئ migration مناسبًا؛ تطبيق قيود uniqueness مباشرة على بيانات تحتوي على تكرارات سيفشل حتى تتم معالجة التكرارات.

## التحقق المنفذ

تم التحقق من نجاح `npm run lint` و`npm run test:security` و`npm run build`. يظل تحذير حجم بعض chunks قائمًا لأن التطبيق يضم وحدات PDF وExcel ورسوميات كبيرة، لكن تم فصل المكتبات الثقيلة إلى chunks مستقلة لتحسين التحميل التدريجي.

## إعداد تسجيل الدخول عبر Google

من [Firebase Console](https://console.firebase.google.com/) افتح المشروع `psyched-plexus-9x6pd`، ثم انتقل إلى **Authentication → Settings → Authorized domains** وأضف نطاق التشغيل الفعلي. في التشغيل المحلي أضف `localhost` و`127.0.0.1` عند الحاجة. في الاستضافة أضف اسم النطاق فقط دون `https://` أو مسار الصفحة، مثل `app.example.com`. بعد ذلك انتقل إلى **Authentication → Sign-in method**، فعّل مزود **Google**، واختر بريد دعم المشروع، ثم احفظ.

يجب فتح التطبيق من نفس خادم Node الذي يشغّل الـAPI؛ لا تفتح `dist/index.html` مباشرة من مدير الملفات، لأن ذلك يشغّل الواجهة دون `/api`. شغّل `npm run dev` ثم افتح العنوان الذي يظهره الخادم، أو شغّل `npm run build` ثم `npm start` وافتح `http://localhost:3000`. إذا ظهرت رسالة اتصال، فغالبًا أن الخادم لم يبدأ أو أن متغيرات PostgreSQL في `.env` ناقصة أو غير صحيحة.

## إنشاء المدير الأول من الهاتف

يمكن إنشاء أول حساب إداري من الهاتف عبر الصفحة الآمنة `/setup-admin`. من إعدادات خدمة Render أضف متغيرًا باسم `ADMIN_BOOTSTRAP_TOKEN` واستخدم قيمة عشوائية طويلة لا تقل عن 32 حرفًا. بعد اكتمال النشر افتح `https://YOUR-SERVICE.onrender.com/setup-admin`، وأدخل رمز الإعداد والاسم والبريد واسم المستخدم وكلمة مرور لا تقل عن 12 حرفًا. بعد إنشاء أول حساب admin تُغلق الصفحة تلقائيًا وتعيد أي محاولة لاحقة رسالة تفيد بأن الإعداد مغلق. احذف `ADMIN_BOOTSTRAP_TOKEN` من Render بعد إنشاء الحساب الأول، ثم سجّل الدخول من الصفحة الرئيسية بالمستخدم المحلي.

لا ترسل رمز الإعداد أو كلمة المرور أو بيانات PostgreSQL في المحادثات، ولا تضعها داخل GitHub.
